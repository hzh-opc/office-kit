# desen-stop 从「文件分发」到「平台启用」操作指引

> 适用范围：本机或任何新机器，`git clone` + `./bootstrap.sh` 已完成（或已手动把
> `hooks/desen-stop/` 分发到 `~/.workbuddy/hooks/desen-stop/`）之后。
> 目的：让 desen-stop Stop Hook 真正被 WorkBuddy 加载执行（而不只是文件就位）。

---

## 0. 一句话结论（为什么需要这步）

`bootstrap.sh` 只完成 **文件分发**：把 desen-stop 插件包复制到
`~/.workbuddy/hooks/desen-stop/`。但平台**只在插件被"导入/启用"、注册进
`enabledPlugins` / `installed_plugins.json` 后才加载其 Stop hook**。

> 已核实的平台事实（2026-09-06 本机）：
> - `~/.workbuddy/settings.json` 的 `enabledPlugins`（形如
>   `{"插件名@来源": true, ...}`）是「已启用插件」的注册清单；
> - `~/.workbuddy/plugins/installed_plugins.json` 记录每个已装插件的
>   `installPath`（位于 `~/.workbuddy/plugins/cache/<来源>/<插件>/<版本>/`）；
> - 当前已启用的插件（agent-browser / sheetagent / playwright-cli 等）全都通过
>   **插件管理页**完成安装+启用，没有任何一个能靠「单纯放目录」生效。
> - security-scan（git commit-hook）**不在** enabledPlugins 里——它走的是 git hook
>   通道，与会话 Stop Hook 不是同一机制，不能作为「放目录即生效」的参照。

文件就位 ≠ 平台生效。启用是**一次性人工动作**，下述两种路径二选一。

---

## 1. 前置确认（先自检分发是否完整，再启用）

desen-stop 插件包必须包含 4 个文件，缺一即导入失败：

```bash
ls -la ~/.workbuddy/hooks/desen-stop/
# 期望看到：
#   .codebuddy-plugin/plugin.json      ← 插件契约入口（平台识别插件靠它）
#   hooks/hooks.json                   ← 声明 Stop 事件命令
#   scripts/desen_stop_hook.py         ← 实际执行脚本
#   README.md                          ← 说明（可选）
```

若缺文件，先重跑 `./bootstrap.sh`（幂等覆盖会补齐仓库最新版），或手动：
```bash
rm -rf ~/.workbuddy/hooks/desen-stop
cp -R <office-kit仓库>/hooks/desen-stop ~/.workbuddy/hooks/
```

自检脚本能否运行（可选，非必需）：
```bash
export PYTHONDONTWRITEBYTECODE=1
python3 ~/.workbuddy/hooks/desen-stop/scripts/desen_stop_hook.py < /dev/null
# 期望：能读到空输入、退出码 0（无内容即无外发判定，静默放行）
```

## 2. 平台启用（核心步骤）

> GUI 路径的平台入口名称可能随 WorkBuddy/CodeBuddy 版本微调，但**本质都是
> 「导入/添加一个本地插件目录」，指向 `~/.workbuddy/hooks/desen-stop/`**。

### 路径 A（推荐）：插件管理页 → 导入本地插件

1. 打开 WorkBuddy，进入**左侧「插件 / 插件管理 / 连接器」**入口（即平时管理
   agent-browser / 腾讯文档等插件的地方）。
2. 找到 **「导入 / 添加本地插件 / 从文件夹安装」**（不同版本叫法略异，含义相同：
   导入一个磁盘上的插件包目录）。
3. 选择目录：**`~/.workbuddy/hooks/desen-stop`**（即 bootstrap 分发好的那整个目录）。
4. 确认导入后，在已装插件列表里应出现 **desen-stop**（category: security）。
5. 在插件列表中把它 **「启用 / Enable」**。
6. （若平台支持配置环境变量）可设 `DESEN_STOP_HOOK_MODE=warn`（默认）或
   `=block`（升级为命中即阻止停止）。

### 路径 B：确认本机是否已有「本地插件源目录」扫描

个别版本可能支持把某个目录设为「本地插件源」，插件置于其下即被扫描发现。
若你的版本有该能力，把 `desen-stop` 整个目录放入该源目录再启用即可。
（本机未观察到该能力的既有证据，优先用路径 A。）

## 3. 启用后的验证（务必做，确认真的生效）

启用后，用**开关式自检**确认 Stop hook 是否被平台加载：

**验 1：注册清单出现 desen-stop**
```bash
python3 -c "import json; d=json.load(open('$HOME/.workbuddy/settings.json')); print([k for k in d.get('enabledPlugins',{}) if 'desen' in k])"
# 期望输出类似： ['desen-stop@<来源>']   ← 空列表说明还没启用到
python3 -c "import json; d=json.load(open('$HOME/.workbuddy/plugins/installed_plugins.json')); print([k for k in d.get('plugins',{}) if 'desen' in k])"
# 期望输出类似： ['desen-stop@...']
```

**验 2：行为验证（更强）**
在一个会话末尾故意做「已外发但无 desen 留痕」的动作（例如让助手处理含身份证/手机号的
文本后直接声称要结束），若平台加载了 desen-stop，会话结束时会输出一条
**`⚠ desen-stop` 警示**（提示本次外发无脱敏留痕）。看到该警示 = 生效；全程无任何
desen 提示 = 未加载，回第 2 步排查。

## 4. 生效模式说明

| 环境变量 | 取值 | 效果 |
|---|---|---|
| `DESEN_STOP_HOOK_MODE` | `warn`（默认） | 命中「有外发无留痕」仅输出警示、允许结束 |
| `DESEN_STOP_HOOK_MODE` | `block` | 命中即阻止结束（exit 2），强制回补 desen 审计 |
| `DESEN_STOP_HOOK_OFF` | `1` | 完全跳过本 hook |

> 环境变量需在**启动 WorkBuddy 的进程环境**里可被 hook 读到（hook 是独立子进程，
> 读的是它自己的环境）。若走 GUI 启动，建议在插件配置/系统级设置里设，而非仅 shell 里 export。

---

## 5. 常见问题排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 验 1 空列表 | 未完成第 2 步启用（只复制了文件） | 回第 2 步，导入本地插件包并启用 |
| 导入时平台不识别 | `~/.workbuddy/hooks/desen-stop/` 缺 `.codebuddy-plugin/plugin.json` 或目录不完整 | 回第 1 步重跑 bootstrap 补齐 4 文件 |
| 验 2 无警示 | 插件已装但 hook 未触发 / 环境变量没生效 | 确认 Stop 事件类型正确；确认 `DESEN_STOP_HOOK_OFF` 未设；重启会话重试 |
| 误报太多 | 关键词近似检测（`read_table` 等） | 按 README 收紧脚本内 `_EXTERNAL_HINTS`；或设 `=block` 前先用 `warn` 观察 |

## 6. 一键校验脚本（把第 1、3 步串起来）

> 可随 bootstrap 后续补一个 `desen-stop/verify.sh`，把下述自检做成一条命令，供新机器
> 部署后跑一遍确认「分发完整 + 已进注册清单」。目前先作为指引，未写脚本文件。

```bash
# 复用片段（shell），未落盘
echo "── 分发完整性 ──"
for f in .codebuddy-plugin/plugin.json hooks/hooks.json scripts/desen_stop_hook.py; do
  test -f "$HOME/.workbuddy/hooks/desen-stop/$f" && echo "  ✓ $f" || echo "  ✗ 缺 $f"
done
echo "── 注册状态（空=未启用）──"
python3 -c "import json;d=json.load(open('$HOME/.workbuddy/settings.json'));print('  enabledPlugins:',[k for k in d.get('enabledPlugins',{}) if 'desen' in k])"
python3 -c "import json;d=json.load(open('$HOME/.workbuddy/plugins/installed_plugins.json'));print('  installed:',[k for k in d.get('plugins',{}) if 'desen' in k])"
```

## 附：为何不直接在 bootstrap.sh 里改 enabledPlugins？

`installed_plugins.json` / `enabledPlugins` 是**平台运行时维护**的注册清单（含版本号、
installPath、安装时间戳，且与 cache 目录结构强关联）。bootstrap 脚本若强行写入，
容易：
1. 与平台缓存的实际插件版本/来源不匹配，导致平台启动时读不到对应 cache 而失效；
2. 破坏平台对插件生命周期的管理（升级/禁用/卸载），产生脏状态；
3. 字段结构/来源命名约定随版本变化，硬编码易过时。

因此正确的做法是**让平台经正规导入流程登记**（第 2 步），脚本只负责把插件包
「分发到位」（可做、已做），把「注册生效」留给平台的插件管理入口。

> 若未来确认某版本有**官方支持的、可脚本化的本地插件注册入口**，可在那时把第 2 步
> 收进 bootstrap，本文档相应降级。在此之前，第 2 步为一次性的 GUI 人工动作。
